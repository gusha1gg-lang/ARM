# Аутентификация, пользователи и роли (Этап 3)

Реализовано: вход/выход, хеширование паролей, сессии, три роли (`viewer`,
`editor`, `admin`), управление пользователями через веб-интерфейс и перенос
старого администратора из legacy-таблицы `UserPass`.

Модули: `app/auth.py`, `app/security.py`, `app/users.py`.
Шаблоны: `app/templates/login.html`, `app/templates/users.html`.
Скрипт переноса: `scripts/migrate_legacy_admin.py`.

## 1. Таблица `users`

Новая таблица (в Access её не было), добавлена в `scripts/schema.sql`:

```sql
CREATE TABLE users (
    user_id       INTEGER PRIMARY KEY AUTOINCREMENT,
    username      TEXT    NOT NULL UNIQUE,
    password_hash TEXT    NOT NULL,
    role          TEXT    NOT NULL CHECK (role IN ('viewer','editor','admin')),
    is_active     INTEGER NOT NULL DEFAULT 1,
    created_at    TEXT    NOT NULL DEFAULT (datetime('now')),
    last_login    TEXT
);
```

* `password_hash` — PBKDF2-SHA256 (`werkzeug.security.generate_password_hash`),
  пароли в открытом виде не хранятся и не логируются.
* `is_active = 0` — учётная запись заблокирована: вход невозможен, активная сессия
  сбрасывается при следующем запросе.
* `last_login` обновляется при успешном входе (`datetime('now')`, UTC).

Legacy-таблица `UserPass` **не изменялась**: она мигрирована 1-в-1 (1 строка) и
остаётся в базе как историческая.

## 2. Вход и выход

| Действие | URL | Поведение |
|---|---|---|
| Форма входа | `GET /Login.aspx` | 200; уже вошедшего перенаправляет на главную |
| Вход | `POST /Login.aspx` | проверка логина/пароля; успех → сессия + редирект, ошибка → тот же текст, что в оригинале |
| Выход | `POST /logout` | очистка сессии + редирект на `/Login.aspx` |

* Текст ошибки дословно из оригинала: «А вот и не угадал. Доступ ограничен.»
* Логин сравнивается без учёта регистра (`COLLATE NOCASE`).
* Редирект после входа — только на локальные пути (`_safe_next`), защита от open redirect.
* Сессия: `HttpOnly`, `SameSite=Lax`; секретный ключ — из `.env` (`SECRET_KEY`).
* Аноним при обращении к защищённой странице получает `302` на
  `/Login.aspx?next=<исходный адрес>`.

## 3. Роли и права

| Роль | Просмотр всех разделов | Добавление / правка / удаление | Управление пользователями |
|---|:---:|:---:|:---:|
| `viewer` | ✅ | ❌ (`403`) | ❌ (`403`) |
| `editor` | ✅ | ✅ | ❌ (`403`) |
| `admin` | ✅ | ✅ | ✅ |

Реализация — декораторы в `app/security.py`:

* `@login_required` — только вошедшим (иначе редирект на вход);
* `@roles_required("editor", "admin")` — иначе `403`;
* `@min_role("editor")` — «роль не ниже» (используется как удобная обёртка).

На формах и в списках кнопки правки отдаются только `editor`/`admin`;
`viewer` видит страницы в режиме чтения. Серверная проверка выполняется всегда,
даже если кнопка скрыта: прямой `POST` от `viewer` даёт `403`.

## 4. Управление пользователями

Страница `/admin/users/` доступна только `admin` (ссылка «Пользователи» в шапке).
Возможности:

| Действие | Маршрут | Ограничения |
|---|---|---|
| Список пользователей | `GET /admin/users/` | только admin |
| Создание | `POST /admin/users/create` | логин уникален (без учёта регистра), пароль ≥ 6 символов, роль из списка |
| Смена роли | `POST /admin/users/<id>/role` | нельзя снять `admin` с последнего активного администратора |
| Сброс пароля | `POST /admin/users/<id>/password` | пароль ≥ 6 символов |
| Блокировка / разблокировка | `POST /admin/users/<id>/toggle` | нельзя заблокировать самого себя и последнего администратора |

Все формы содержат CSRF-токен; при его отсутствии/несовпадении — `400`.

### Как добавить пользователя и назначить роль

1. Войти как `admin`.
2. В шапке нажать **«Пользователи»** (`/admin/users/`).
3. В блоке **«Добавить пользователя»** заполнить:
   * **Логин** — например, `ivanov`;
   * **Пароль** — не короче 6 символов;
   * **Роль** — `viewer`, `editor` или `admin` (по умолчанию `viewer`).
4. Нажать **«Создать»** — пользователь появится в таблице.
5. Роль можно изменить в любой момент: выпадающий список в колонке «Роль»
   применяется сразу. Пароль меняется кнопкой **«Сменить пароль»**,
   доступ — кнопкой **«Заблокировать»/«Разблокировать»**.

Первый администратор создаётся скриптом из legacy-таблицы `UserPass`:

```powershell
python scripts/migrate_legacy_admin.py
```

Скрипт идемпотентен: если логин уже есть в `users`, запись пропускается.
Пароль остаётся прежним (как в старой базе) — смените его после первого входа.

## 5. Защита от ошибок администрирования

* Нельзя заблокировать самого себя.
* Нельзя снять роль `admin` с последнего активного администратора.
* Нельзя заблокировать последнего активного администратора.
* При деактивации пользователя его открытая сессия сбрасывается
  (`load_logged_in_user` не находит активную запись → `session.clear()`).
* Удаление пользователей не предусмотрено — только блокировка (история сохраняется).

## 6. Отклонения от оригинала (осознанные)

| № | Отклонение | Причина |
|---|---|---|
| 1 | Вместо одного администратора (`Session["admin"]`) — таблица `users` и три роли | Требование многопользовательского режима |
| 2 | Пароли хранятся как PBKDF2-SHA256-хеш | Безопасность; в оригинале пароль лежал в `UserPass` открытым текстом |
| 3 | CSRF-токены во всех формах, включая вход | Безопасность |
| 4 | Ошибка входа не уточняет, что неверно (логин или пароль) | Не давать подсказок для подбора |
| 5 | Добавление/правка/удаление данных доступны `editor`, а не только admin | Требование ролей; фиксируется по страницам в `docs/04_PAGES.md` |
| 6 | Заблокированные пользователи не удаляются | Сохранение истории и возможности вернуть доступ |
