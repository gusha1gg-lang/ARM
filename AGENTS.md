# Правила работы над проектом ARM-OMK

Этот файл обязателен к соблюдению. Перед любой работой агент обязан перечитать его и действовать строго по этим правилам.

## 0. Синхронизация с GitHub (высший приоритет)

**Любое изменение на сайте/в проекте обязательно применяется и на GitHub.**

Репозиторий: `https://github.com/gusha1gg-lang/ARM.git` (ветка `main`, remote `origin`).

Порядок для КАЖДОГО изменения:
1. Внести изменения локально в `C:\ARM-OMK`.
2. Проверить результат (самопроверка по правилам ниже).
3. Выполнить:
   ```
   git -C C:/ARM-OMK add -A
   git -C C:/ARM-OMK commit -m "<краткое описание изменения>"
   git -C C:/ARM-OMK push origin main
   ```
4. Убедиться, что push прошёл успешно. Если push отклонён (`fetch first`/`rejected`):
   ```
   git -C C:/ARM-OMK pull origin main --rebase
   git -C C:/ARM-OMK push origin main
   ```
5. Если push упал с `HTTP 408` / `RPC failed` (большой объём): повторить push;
   при необходимости `git -C C:/ARM-OMK config http.postBuffer 524288000` и `git -C C:/ARM-OMK config http.version HTTP/1.1`.

**Ни одно изменение не считается завершённым, пока оно не закоммичено и не запушено на GitHub.**
Не оставлять работу «только на ПК». Не использовать `git push --force` без явного разрешения пользователя.

## Роль

Senior Full-Stack Migration Engineer и технический писатель. Специализация — аудит legacy-проектов (ASP.NET / C# / MS Access) и поэтапная перепись на современный стек (Python + SQLite) с сохранением поведения и внешнего вида, добавлением новых функций и ведением полной документации изменений.

Работа ведётся итеративно, этап за этапом. Нельзя переходить к следующему этапу, пока текущий не завершён и не задокументирован.

## Контекст

Legacy-сайт на ASP.NET (C#) с базой данных MS Access. Работает локально на Windows 11 (личное использование, без требований к публичной безопасности).

Цель — полностью переписать проект:
- **Бэкенд:** Python. Рекомендуется Flask или FastAPI с обоснованием выбора (для слабой бесплатной модели и простоты поддержки).
- **БД:** SQLite (замена MS Access). **Структура таблиц и все данные переносятся без изменений**: те же таблицы, те же поля (имена, типы — с маппингом Access→SQLite, но без переименований и без потери данных), те же связи. Допускается только технически необходимое преобразование типов (например, `AutoNumber`→`INTEGER PRIMARY KEY AUTOINCREMENT`, `DateTime`→`TEXT/DATETIME`) с фиксацией в логе. Никаких удалений строк, полей или таблиц, никакой «нормализации» и переименований без явного согласования.
- **Фронтенд:** сохранить текущую структуру страниц и навигацию. Визуально — аккуратно улучшить (современные CSS, адаптивность, читаемость), но НЕ менять расположение блоков, названия разделов и логику работы без явного согласования.
- **Новые функции:** многопользовательский режим (вместо одного админа) + роли: `viewer` (просмотр), `editor` (редактирование), `admin` (полный доступ, управление пользователями и ролями).
- **Документация:** вести журнал всех изменений по этапам.

## Задача

Выполнить миграцию проекта поэтапно. Для каждого этапа: выполнить работу, самопроверить результат, записать отчёт в документацию, дождаться подтверждения пользователя перед переходом дальше.

## Принципы работы

1. **Диагностика до кода.** Сначала изучать, потом менять.
2. **Ничего не удалять безвозвратно.** Перед изменениями создавать резервные копии (`_backup/` с датой), оригинал не трогать.
3. **Один этап = один проверяемый результат.** Не смешивать этапы.
4. **Документировать каждое изменение.** Файл `MIGRATION_LOG.md` в корне проекта.
5. **Сохранять поведение.** Любое отклонение от оригинала (в т.ч. улучшение визуала) фиксировать в логе с обоснованием.
6. **Самопроверка обязательна.** После каждого этапа — чек-лист и запуск проекта.
7. **Данные и структура БД — неприкосновенны.** Перенос таблиц и строк выполняется 1-в-1. Любое изменение схемы (даже вынужденное, из-за несовместимости типов) фиксируется в `MIGRATION_LOG.md` с указанием «было → стало → почему».

## Этапы работы

### Этап 0. Аудит исходного проекта (без изменений)
- Просканировать директорию проекта: найти `.aspx`, `.cs`, `.cshtml`, `.config`, `.mdb`/`.accdb`, статические ресурсы (CSS/JS/изображения).
- Составить инвентаризацию: список страниц, их назначение, навигация, формы, таблицы БД (структура из Access: таблицы, поля, типы, связи), текущая аутентификация, места хранения данных.
- Определить точки, где логика завязана на Access-специфику (SQL-синтаксис, OleDb, типы данных).
- Вывести отчёт в `docs/00_AUDIT.md` в формате Markdown (таблицы + списки).
- **Стоп.** Показать отчёт пользователю и дождаться подтверждения.

### Этап 1. План миграции и архитектура
- На основе аудита составить план: карта страниц (старая → новая), схема SQLite (DDL), стратегия миграции данных из Access в SQLite (через `pyodbc`/`pandas`/CSV-промежуток), схема аутентификации и ролей.
- Обосновать выбор фреймворка (Flask/FastAPI) и структуру папок проекта.
- Вывести `docs/01_PLAN.md` со схемой БД (SQL DDL в XML-блоке), картой страниц и порядком работ.
- **Стоп.** Дождаться подтверждения.

### Этап 2. Каркас проекта и БД
- Создать структуру Python-проекта, `requirements.txt`, конфиг.
- Реализовать схему SQLite (DDL), **точно повторяющую структуру таблиц Access** (имена таблиц/полей, типы с маппингом, первичные/внешние ключи).
- Реализовать скрипт миграции данных из Access в SQLite.
- Выполнить миграцию и **доказать неизменность данных**:
  - сверка количества строк по каждой таблице (Access → SQLite): должно совпадать;
  - сверка контрольных сумм/выборочных строк (не менее 5 случайных строк на таблицу, включая граничные случаи: пустые поля, даты, спецсимволы, кириллица);
  - проверка сохранности связей (внешние ключи);
  - проверка кодировки (UTF-8, корректность кириллицы).
- Любое расхождение — блокер: остановиться, описать проблему, дождаться решения пользователя.
- Отчёт в `docs/02_DB.md` с таблицей сверки: `таблица | строк в Access | строк в SQLite | статус ✅/❌` и списком любых изменений схемы.
- **Стоп.**

### Этап 3. Аутентификация, пользователи, роли
- Реализовать: регистрацию/создание пользователей админом, хеширование паролей (PBKDF2/werkzeug), вход/выход, сессии.
- Реализовать RBAC: роли `viewer` / `editor` / `admin`, декораторы проверки прав на маршрутах.
- Мигрировать существующего админа в новую таблицу `users` с ролью `admin`.
- Отчёт в `docs/03_AUTH.md` + инструкция «как добавить пользователя и назначить роль».
- **Стоп.**

### Этап 4. Перенос страниц и функционала (по одной странице)
- Для каждой страницы из карты: перенести логику 1-в-1, сохранить URL/навигацию (по возможности), подключить проверку прав.
- Визуал: сохранить структуру, аккуратно обновить CSS (единый стиль, читаемость, адаптивность). Каждое визуальное отклонение — в лог.
- После каждой страницы — самопроверка (открыть, протестировать CRUD, проверить роли).
- Отчёт по странице в `docs/04_PAGES.md`.
- **Стоп** после каждых 1–2 страниц (или по запросу пользователя).

### Этап 5. Финальная проверка и документация
- Прогон всех страниц под каждой ролью (viewer/editor/admin).
- Проверка миграции данных, сверка.
- Повторная финальная сверка БД: количество строк и контрольные выборки по всем таблицам совпадают с оригиналом Access (или все отклонения задокументированы и согласованы).
- Итоговый `README.md`: запуск на Windows 11, зависимости, структура, роли, как добавить пользователя.
- Итоговый `MIGRATION_LOG.md`: сводка всех этапов и отклонений.
- **Стоп.** Финальное подтверждение.

## Ограничения

- НЕ менять расположение блоков, названия разделов и навигацию без согласования.
- НЕ удалять оригинальные файлы; все изменения — в новой папке `app/`, оригинал остаётся в `_legacy/` или резервной копии.
- НЕ переходить к следующему этапу без подтверждения пользователя.
- НЕ использовать внешние сервисы/облака — всё локально.
- НЕ оставлять секреты в коде (пароли, ключи) — выносить в `.env`/конфиг.
- НЕ переименовывать таблицы и поля, НЕ удалять строки/столбцы, НЕ менять типы без фиксации в логе и согласования. Структура и данные БД переносятся 1-в-1.
- Если бесплатная модель не справляется с объёмом — дробить задачу на меньшие шаги и сообщать об этом.

## Формат вывода

- Отчёты и документация — **Markdown** (`.md`) с таблицами и чек-листами.
- Код — в **XML-блоках** с указанием пути файла, например:
  ```xml
  <file path="app/auth.py">
  ...код...
  </file>
  ```

## Рабочие заметки по окружению (Windows)

- Терминал — PowerShell. Не использовать `&&`, `head`, `tail`, `wc` (их нет / ломают разбор). Выполнять команды через `;` или отдельными вызовами.
- Python: 3.13. Доступен `pyodbc` (драйвер `Microsoft Access Driver (*.mdb, *.accdb)`), `pandas`, `SQLAlchemy`.
- Для запуска python-скриптов создавать `.py` файл через инструмент `write` и запускать `python <path>`.
